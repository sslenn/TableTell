Real-Time SSE (Server-Sent Events) Data Streaming Lifecycle

Unlike standard REST APIs where the client waits silently for 10 seconds, TableTell establishes an open text/event-stream connection. The client receives live state transitions, SQL syntax before execution, self-healing retries, and token-by-token narrative explanations.

STEP 1 Client Dispatches Analytical Request via POST
useChatStream.ts triggers fetchEventSource('/api/chat/stream') passing the natural language question, active dataset ID (e.g. ecommerce_sales), and conversation history.
STEP 2 Event: event: status (planning)
FastAPI returns an immediate HTTP 200 chunked stream. LangGraph reads the dataset schema from DuckDB, mounts the system prompt, and prompts Google Gemini to write DuckDB SQL. 
event: status
data: {"step": "planning", "message": "Formulating DuckDB SQL plan from schema digest..."}
STEP 3 Event: event: sql
Gemini outputs the SQL query. The backend emits the raw SQL to the frontend immediately so the user can inspect the query in the SqlHighlighter before execution starts. 
event: sql
data: {"sql": "SELECT category, SUM(revenue) AS total_rev FROM active_dataset GROUP BY 1 ORDER BY 2 DESC"}
STEP 4 (Conditional) Event: event: self_heal
If DuckDB encounters a syntax error, binder error, or missing column, the LangGraph execute_sql_node intercepts the traceback and passes it to self_heal_node. It repairs the query and emits the retry status live to the UI! 
event: self_heal
data: {"status": "repairing", "error": "Binder Error: column 'revenue' not found", "repaired_sql": "SELECT category, SUM(total_sales) ...", "retry_count": 1}
STEP 5 Event: event: token (Streaming Explanation)
Once DuckDB executes successfully, Gemini streams narrative business takeaways word-by-word into the client's message bubble. 
event: token
data: {"token": "Electronics "}

event: token
data: {"token": "generated "}

event: token
data: {"token": "$142,500 "}
STEP 6 Event: event: complete (Plotly Visualization Payload)
LangGraph synthesizes dynamic Plotly configurations based on query dimensionality (temporal line chart, categorical bar chart, or metric card). The stream closes with complete latency metrics. 
event: complete
data: {
  "reply": "Electronics generated $142,500 in total sales, outperforming Home Goods by 34%...",
  "sql": "SELECT category, SUM(total_sales) ...",
  "visualization": { "chart_type": "bar", "plotly_spec": { "data": [...], "layout": {...} } },
  "execution_time_ms": 482
}

Module / Service Role & Connection

💾 The Inverted Lakehouse Storage Architecture

1. IMMUTABLE RAW PRESERVATION

backend/data_lake/raw/

Uploaded CSV or Excel files are stamped with UUIDs and stored permanently. Transformations never mutate raw files, guaranteeing non-destructive data lineage.

2. VERSIONED COLUMNAR LAKE

backend/data_lake/processed/

Converted to Snappy-compressed Apache Parquet. Every approved cleaning run increments the dataset version (e.g. data_v1.parquet $\rightarrow$ data_v2.parquet).

3. RELATIONAL LINEAGE & AUDIT

backend/data_lake/metadata/

SQLite database (tabletell_metadata.db) tracks dataset schemas, cleaning plan proposals, user approvals, execution durations, and assistant chat history.
