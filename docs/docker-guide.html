The idea in one minute

Your app only works if the computer running it has the right Python version, the right Node version, the right packages, and the right folders. On your laptop that is true. On a new server it usually is not, and you spend an afternoon fixing it.

Docker solves this by sealing the app and everything it needs into one package. That package runs the same way on your Windows PC, on a colleague's Mac, and on a rented Linux server.

Why not a virtual machine?

A virtual machine (VM) pretends to be a whole computer, including its own full operating system. A container does not. It borrows the operating system core (the kernel) from the computer it runs on and only packs the app and its libraries. That is why containers are small (tens or hundreds of megabytes instead of gigabytes) and start in seconds.

On your Windows PC

Containers need a Linux kernel. Docker Desktop on Windows quietly runs a small hidden Linux machine (WSL 2) and puts your containers inside it. This is why TableTell's image is built on Linux (python:3.13-slim is Debian Linux), and why your Windows node_modules and backend/.venv folders must never be copied into the image. Your .dockerignore already excludes them.

The words you will hear

Docker Engine, the daemon, and the CLI

When you type docker something, you are using the CLI (command line tool). It does no work itself. It sends your request to the daemon (dockerd), a background program that builds images and runs containers. Together with the supporting parts, this is the Docker Engine. If a command says it cannot connect to the Docker daemon, Docker Desktop (or the service on a server) is not running.

Image

A read-only snapshot containing an operating system's files, your programs, and your settings. You build it once and can start it many times. You cannot change an image after it exists. You build a new one instead.

Container

A running (or stopped) instance of an image. Docker adds a thin writable layer on top of the image for that container's own changes, and that layer is thrown away when the container is deleted.

Registry and tag

A registry stores images. Docker Hub is the default one. An image name looks like python:3.13-slim: the part before the colon is the name, the part after is the tag (a version label). Tags like latest or 3.13-slim can move to newer builds over time.

Volume and bind mount

Ways to keep files outside the container so they survive. Covered in its own section.

Network

The private wiring between containers, and between containers and the outside world. Covered in its own section.

Compose

A tool that reads one YAML file and starts everything for you with a single command, so you do not retype long docker run commands.

Images are stacks of layers

Every instruction in a Dockerfile that changes files (RUN, COPY) adds one layer to the image. Layers stack, and Docker saves each one.

The rule that makes builds fast: if an instruction and the files it uses have not changed since last time, Docker reuses the saved layer. The moment one layer changes, that layer and every layer above it are rebuilt.

The Dockerfile, line by line

A Dockerfile is a list of steps, run top to bottom, that builds an image. These are the instructions you need to know, with where TableTell uses them.

RUN happens once, when you build. CMD happens every time a container starts. Mixing these up is the most common beginner mistake.

The .dockerignore file

Before building, Docker sends your project folder to the daemon. .dockerignore lists what to leave out, like .gitignore does for Git. It keeps images small, speeds up builds, and keeps private files out. Yours excludes .git, backend/.venv, frontend/node_modules, and frontend/dist. It is missing one important line, covered in the findings.

Multi-stage builds

Building your React website needs Node.js and hundreds of megabytes of packages. Running it needs none of that, because the result is plain HTML, JavaScript and CSS files. A multi-stage build uses two FROM lines: the first stage builds, the second stage is the real image, and only the files you choose to copy across make it in.

Containers and their life

A container has a small set of states. Knowing them tells you what each command does.

Things worth remembering

  • Containers are disposable. To update TableTell you do not patch the running container. You build a new image and replace the container.
  • One main process per container. When that process exits, the container stops. If a container stops right after starting, the app crashed. Run docker logs to see why.
  • localhost inside a container means the container itself, not your computer.

Volumes: keeping your data

A container's own files vanish when it is removed. TableTell stores uploaded datasets, converted Parquet files and a SQLite database of dataset records. Losing those on every update would be a disaster, so they live in a folder outside the container.

Two kinds of storage

Looks like./data_lake:/app/... (starts with a path)mydata:/app/... (just a name)

What deletes your data

docker compose down removes containers and the network but never deletes a bind-mounted folder. docker compose down -v also deletes named volumes, but not bind mounts. The real risks for ./data_lake are deleting the folder yourself, running the project from a different directory (a different ./data_lake), or forgetting to back it up.

To back up safely, stop the container first (docker compose stop), then copy the whole data_lake folder. Copying a SQLite file while the app is writing to it can give you a damaged copy.

Ports and networking

A container is sealed. Nothing from outside can reach it unless you open a door. Three words describe the doors:

  • EXPOSE / expose: a label that says "the app listens on 8000". Other containers on the same Docker network can connect. Your computer and the internet cannot.
  • ports: "HOST:CONTAINER" actually publishes the port on the server. "8000:8000" means server port 8000 forwards to container port 8000.
  • HOST=0.0.0.0 is a setting inside the app. It must listen on all addresses, not just 127.0.0.1, or nothing outside the container can reach it. Your run.py defaults to 0.0.0.0, which is correct.
Publishing a port can bypass your firewall

On Linux, Docker edits the firewall rules itself when it publishes a port. A plain "8000:8000" listens on every network interface, and can be reachable from the internet even when a firewall tool such as ufw says it is blocked. Use "127.0.0.1:8000:8000" so only the proxy on the same machine can reach it.

Docker Compose

Without Compose you would type a long docker run command with ports, folders and settings every time. Compose stores all of that in docker-compose.yml. Yours, with notes:

services:
  tabletell:                      # the service name; also its hostname on the network
    build:
      context: .                  # send the whole project folder to the build
      dockerfile: Dockerfile
      args:
        - VITE_CLERK_PUBLISHABLE_KEY=${VITE_CLERK_PUBLISHABLE_KEY:-}   # build-time setting
    restart: unless-stopped       # restart after crashes and reboots, unless you stopped it
    expose:
      - "8000"                    # reachable by other containers only
    environment:                  # run-time settings, read from your shell or .env
      - GEMINI_API_KEY=${GEMINI_API_KEY:-}
      - CLERK_SECRET_KEY=${CLERK_SECRET_KEY:-}
      - HOST=0.0.0.0
      - PORT=8000
      - ENVIRONMENT=production
    volumes:
      - ./data_lake:/app/backend/data_lake    # your data survives rebuilds
    env_file:
      - path: .env
        required: false           # fine if the file is missing
    healthcheck:
      test: ["CMD-SHELL", "curl -f http://localhost:8000/api/health || exit 1"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 15s           # grace time while the app boots

${NAME:-} means "use the value of NAME, or an empty string if it is not set". Compose reads values from your shell and from a file called .env next to the compose file.

The commands you will use daily

docker compose up -d --build     # build the image, start the container in the background
docker compose ps                # is it running? is it healthy?
docker compose logs -f tabletell # watch the app's output live (Ctrl+C to stop watching)
docker compose restart tabletell # restart without rebuilding
docker compose down              # stop and remove the container (your data_lake stays)

Use docker compose (with a space). The older docker-compose (with a hyphen) is a previous generation of the tool.

Settings and secrets

The same image should run anywhere, so settings that change (API keys, ports) stay outside it. There are two moments a setting can enter, and mixing them up causes confusing bugs.

Build time (ARG)Run time (environment, env_file)
When it is readWhile docker build runsEach time a container starts
Changing it needsA rebuildOnly a restart
TableTell exampleVITE_CLERK_PUBLISHABLE_KEY. Vite writes it into the JavaScript files.GEMINI_API_KEY, CLERK_SECRET_KEY, PORT, ENVIRONMENT
Safe for secrets?No. Anything built into the website is public. Clerk's publishable key is designed to be public, so it is fine.Yes, this is where secrets belong
Rules that prevent leaks
  • Never write a secret in a Dockerfile (ENV or ARG) or copy a file that contains one into the image. Anyone who gets the image can read it.
  • Keep .env out of Git (yours is) and out of the image (see the findings).
  • Values in environment are visible to anyone who can run docker inspect on the server. That is acceptable for a single-owner server, so keep server access tight.

Health checks, restarts, logs

Health check

Your healthcheck runs curl against /api/health every 30 seconds. The container shows starting, then healthy or unhealthy in docker compose ps. Plain Docker does not restart an unhealthy container. It only reports the state, and tools such as Coolify or Traefik use it to decide where to send traffic.

Restart policy

restart: unless-stopped brings the container back after a crash or a server reboot, but not if you stopped it by hand. It reacts to the process exiting, not to a failing health check.

Logs

Whatever the app prints appears in docker compose logs. That is why the Dockerfile sets PYTHONUNBUFFERED=1: Python then prints immediately instead of holding output back.

By default Docker keeps logs in a file with no size limit, which can slowly fill a small server disk. If you run this for months, add a limit under the service:

    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"

Deploying, step by step

  1. Install Docker and the Compose plugin on the server, and start the Docker service.
  2. Copy the project to the server and create .env from deploy/.env.production.example, filling in your keys.
  3. Run docker compose up -d --build. Docker builds stage 1 (website), builds stage 2 (Python image with the website inside), and starts the container.
  4. Run docker compose ps until the status reads healthy.
  5. Point a reverse proxy (Caddy or nginx) at the container and enable HTTPS. See the networking section for which port setup you need.
  6. To update: pull the new code, run docker compose up -d --build again. The data stays in data_lake.

Why the proxy has special settings

The chat page streams the AI's progress live (Server-Sent Events). A proxy that buffers responses holds that stream back until the whole answer is done. Your nginx file turns buffering off for /api/chat/stream, and your Caddyfile uses flush_interval -1 for the same reason. Both also raise the upload limit to 100 MB, matching MAX_UPLOAD_SIZE_MB in the app.

Problems found in your setup

I read your files looking for gaps. These are ordered by how much they matter. I have not changed any of them.

1. Your .env files can be baked into the image

.dockerignore has no line excluding .env, and the Dockerfile runs COPY backend/ /app/backend/. Your repo contains backend/.env, so it is copied into the image, and any API keys inside travel with the image to wherever it is stored or shared. The same applies to frontend/.env in the build stage, which only holds a publishable key.

Fix: add these lines to .dockerignore and rebuild:

.env
**/.env
!**/.env.example

If an image built this way was ever pushed to a registry or shared, treat the keys in backend/.env as exposed and replace them.

2. The compose file and the proxy files disagree

Compose publishes nothing (expose only), but deploy/Caddyfile, deploy/nginx/tabletell.conf and DEPLOYMENT.md send traffic to 127.0.0.1:8000 on the server. That address will refuse connections. Pick one: if you run Caddy or nginx directly on the server, add ports: - "127.0.0.1:8000:8000". If you deploy through Coolify or another proxy container, keep expose and ignore the Caddy and nginx files.

3. The app runs as root inside the container

The Dockerfile has no USER line. If someone exploits the app, they have root inside the container. DEPLOYMENT.md tells you to chown -R 1000:1000 the data folder, which suggests a non-root user was intended. Adding a user later means the mounted data_lake folder must be writable by that user, so test it before relying on it.

Smaller notes

  • Unused folder. The Dockerfile creates /app/data_lake/..., but the app (via config.py) uses /app/backend/data_lake, which is also where compose mounts your folder. The mkdir line does nothing useful, and the app creates its own folders on startup.
  • Build tools left in the image. gcc is installed in the final image. If every Python package you use ships a ready-made wheel, you can remove it and make the image smaller. Test before removing.
  • Run one copy only. SQLite and DuckDB files on one disk are not designed for several containers writing at once. Do not scale this to multiple replicas on one data folder.
  • npm ci is stricter than npm install. I switched the Dockerfile to npm ci earlier. It fails if package.json and package-lock.json disagree, and I could not test that here. If the build stops with a lockfile error, run npm install in frontend/ on your computer and commit the updated lockfile. (The lockfile does include the Linux packages that the Alpine build stage needs.)
  • Moving tags. python:3.13-slim and node:20-alpine can change underneath you between builds. That is usually fine for a project this size, but it is why a rebuild a month later can behave slightly differently.

When something breaks

The container starts, then stops right away

The app crashed during startup. Run docker compose logs tabletell and read the last lines. Usual causes: a missing setting, a typo in .env, or a Python package error.

I changed code but the site looks the same

You probably restarted without rebuilding. The code lives inside the image, so run docker compose up -d --build. If it still looks old, hard-refresh the browser, since the browser caches JavaScript files.

Status says "unhealthy"

The health check could not reach /api/health. Run docker compose logs tabletell, then docker compose exec tabletell curl -s localhost:8000/api/health to see the answer from inside. A check that works inside but the site does not open from outside points to the port setup in networking.

The proxy says "connection refused" or 502

Either the container is not running or healthy (check docker compose ps), or the port is not published for a proxy that runs on the host. See finding 2 above.

"port is already allocated" or "address already in use"

Something else on the server already uses that port. Find it (sudo ss -ltnp on Linux) and stop it, or publish a different host port, for example "127.0.0.1:8001:8000".

The build fails at npm ci

Usually the lockfile and package.json are out of sync. Run npm install in frontend/ on your computer, commit the new package-lock.json, and build again.

"permission denied" when saving uploads

The user inside the container cannot write to the mounted data_lake folder. Right now the app runs as root, so this mainly appears if you add a USER line later. Fix the folder's owner on the server to match.

My datasets disappeared after an update

Check that you ran compose from the project folder you used before. A different folder has a different ./data_lake. Also check that docker compose config still shows the volume line.

The server disk is full

Run docker system df to see whether images or logs are the cause. Old images build up with every rebuild, and docker system prune clears the safe ones. Large log files are fixed with the logging limit in the health section.

"Cannot connect to the Docker daemon"

Docker is not running. On Windows, start Docker Desktop and wait until it says it is running. On a Linux server, run sudo systemctl start docker.

What to learn next

You now know enough to run, update, and debug TableTell. In rough order of usefulness:

  1. Apply the .dockerignore fix and settle the port question (findings 1 and 2).
  2. Practice docker compose up -d --build, logs and exec on your PC until they feel routine.
  3. Set up a backup of data_lake (stop, copy, start).
  4. Add the non-root USER and the log size limit.
  5. Later, if you automate releases: build the image in CI and push it to a registry, so the server pulls a ready image instead of building.

You can ignore Kubernetes and Docker Swarm. They coordinate many containers across many servers, and TableTell is one container on one server.
